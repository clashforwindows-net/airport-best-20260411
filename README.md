## 节点分布为什么重要

节点是你与目标服务器之间的「中转站」，它的物理位置直接决定：

- **延迟**：物理距离越远，光信号往返越久。
- **绕路**：节点布局差会导致流量绕半个地球。
- **解锁能力**：某些流媒体只认特定地区 IP。
- **稳定性**：单点过载会拖垮整条链路。

**规律**：距离近 ≠ 一定快，但距离远几乎一定慢。合理的多区域分布 = 你在任何场景都能找到最优节点。

## 全球节点地理分布全景

### 主要区域与典型用途

| 区域 | 覆盖城市 | 适合场景 | 到大陆延迟 |
|------|---------|---------|-----------|
| 香港 (HK) | 多家运营商 | 日常 / 游戏 / 流媒体 | 20-50ms |
| 日本 (JP) | 东京 / 大阪 | 游戏 / 通用 | 40-70ms |
| 新加坡 (SG) | 全境 | 东南亚访问 / 通用 | 60-100ms |
| 台湾 (TW) | 台北 | 流媒体 / 游戏 | 30-60ms |
| 韩国 (KR) | 首尔 | 游戏 / 韩区服务 | 40-70ms |
| 美国 (US) | 洛杉矶 / 硅谷 / 纽约 | 美区流媒体 / 开发 | 130-180ms |
| 欧洲 (EU) | 德国 / 荷兰 / 法国 | 欧区服务 | 180-240ms |

### 节点密度 vs 质量

很多机场标榜「100+ 节点」，但：

- 同一城市堆 20 个同质节点 ≠ 质量好
- 关键区域（HK/JP/US）有优质线路才是真价值
- 冷门区域节点多为凑数，实际拥塞严重

**判断标准**：看「核心区域是否有 IEPL / 专线」，而非节点总数。

## 节点质量评估六维模型

| 维度 | 说明 | 优秀标准 |
|------|------|---------|
| 延迟 (Latency) | 往返时间 | HK<50ms, JP<70ms |
| 丢包 (Loss) | 数据包丢失率 | <0.5% |
| 抖动 (Jitter) | 延迟波动 | <10ms |
| 带宽 (Bandwidth) | 实际吞吐 | 单机 ≥100Mbps |
| 负载 (Load) | 在线人数占比 | <70% 满载 |
| 在线率 (Uptime) | 可用性 | >99% |

### 实测数据示例（HK 节点）

| 时段 | 延迟 | 丢包 | 抖动 | 带宽 |
|------|------|------|------|------|
| 凌晨 02:00 | 28ms | 0% | 2ms | 320Mbps |
| 晚高 21:00 | 45ms | 0.1% | 5ms | 180Mbps |
| 周末 20:00 | 52ms | 0.3% | 8ms | 140Mbps |

**结论**：晚高峰仍能保持 <50ms、低丢包，才算优质节点。

## 负载均衡策略详解

### 客户端侧负载均衡

Clash 提供多种负载均衡类型：

```yaml
proxy-groups:
  - name: "负载均衡-URL"
    type: url-test
    url: "https://www.gstatic.com/generate_204"
    interval: 300
    proxies:
      - HK-01
      - HK-02
      - JP-01
      - TW-01

  - name: "负载均衡-轮询"
    type: round-robin
    proxies:
      - HK-01
      - JP-01
      - TW-01
```

| 类型 | 特点 | 适用 |
|------|------|------|
| url-test | 自动选延迟最低 | 日常通用 |
| fallback | 主节点挂了切备用 | 稳定性优先 |
| round-robin | 轮流分配 | 大流量均摊 |
| load-balance | 按连接分摊 | 多任务并发 |

### 服务端负载均衡

优质机场在服务端做：

- 入口按地域分流
- 单节点人数上限控制
- 热点节点自动扩容
- 故障节点自动摘除

## 节点切换技术

### 自动切换

- **url-test**：每 300s 测一次，自动选最优。
- **健康检查**：连续超时自动剔除节点。
- **故障转移**：主链路断连瞬时切备。

### 手动切换

- 按场景手动指定（游戏走 HK，流媒体走 US）。
- 用 Clash 的 `select` 组灵活切换。
- 配合订阅分组管理。

### 智能切换脚本（Python 示例）

```python
import subprocess, re, time

def ping_latency(host):
    out = subprocess.run(["ping", "-n", "4", host],
                         capture_output=True, text=True).stdout
    ms = re.findall(r"=(\d+)ms", out)
    return sum(int(x) for x in ms) / len(ms) if ms else 999

nodes = {"HK": "hk.clashvip.net", "JP": "jp.clashvip.net", "TW": "tw.clashvip.net"}
best = min(nodes, key=lambda k: ping_latency(nodes[k]))
print(f"最优节点: {best}")
```

## 节点健康度监控

### 监控指标看板

| 指标 | 采集方式 | 告警阈值 |
|------|---------|---------|
| 延迟 | 定时 ping | >120ms |
| 丢包 | mtr 统计 | >2% |
| 在线率 | 心跳探测 | <99% |
| 带宽 | 测速脚本 | <50Mbps |

### 持续监控脚本

```bash
#!/bin/bash
# node_health.sh — 每 5 分钟记录一次节点状态
while true; do
  for node in hk jp tw us; do
    ts=$(date '+%Y-%m-%d %H:%M')
    loss=$(ping -n 20 ${node}.clashvip.net | grep "Lost" | awk '{print $5}')
    echo "$ts $node loss=$loss" >> health.log
  done
  sleep 300
done
```

## 节点优选脚本

```bash
#!/bin/bash
# best_node.sh — 批量测速挑最优节点
for node in hk jp tw sg us kr; do
  avg=$(ping -n 10 ${node}.clashvip.net | awk -F'=' '/Average/{print $2}' | tr -d 'ms')
  echo "$node: ${avg}ms"
done | sort -t: -k2 -n
```

## 节点分布避坑指南

### ❌ 坑一：节点数虚标

宣传 200 节点，实际 180 个同质低价线路。看核心区域专线质量，别数数。

### ❌ 坑二：只有美国节点

美区节点对游戏用户延迟 150ms+，毫无体验。必须覆盖亚太。

### ❌ 坑三：节点常年满载

热门节点不扩容，晚高峰丢包 5%+。选有动态扩容的机场。

### ❌ 坑四：假「香港」节点

实为转口中转，延迟 80ms+。用 tracert 看是否真落地香港。

### ✅ 正确做法

- 核心区域要有专线
- 晚高峰实测而非宣传值
- 用 url-test 自动选优
- 关注单节点负载

## 专线、IEPL 与 Anycast 的区别

很多机场宣传「CN2」「IEPL」「专线」，实际差别巨大：

| 类型 | 原理 | 延迟 | 成本 | 体验 |
|------|------|------|------|------|
| 公网中转 | 走公共互联网 | 高且抖 | 低 | 晚高峰塌 |
| CN2 GIA | 电信优质线路 | 低 | 中 | 稳 |
| IEPL 专线 | 点对点物理专线 | 最低 | 高 | 极稳 |
| BGP 多线 | 多运营商融合 | 中 | 中 | 均衡 |
| Anycast | 就近接入 | 低 | 高 | 抗 DDoS |

**判断**：声称「专线」却晚高峰 200ms+，基本是公网伪装。真 IEPL 应有独立 IP 段与稳定低延迟。

## 节点选购决策树

1. 主要用途是游戏？→ 优先 HK/TW/JP 低延迟专线。
2. 主要看流媒体？→ 优先有解锁节点的 US/SG。
3. 主要开发下载？→ 优先 JP 大带宽。
4. 预算有限？→ 选核心区域齐、晚高峰稳的中端。
5. 多设备家庭？→ 选支持路由器部署 + 多端授权。

> 决策核心：先定场景，再选区域，最后看该区域是否为真专线。

## 节点 IP 纯净度

流媒体与部分服务会封禁「数据中心 IP」。节点 IP 类型影响解锁：

| IP 类型 | 解锁率 | 说明 |
|---------|--------|------|
| 住宅 IP | 高 | 难获取、贵 |
| 原生 IP | 高 | 该区域注册 IP |
| 广播 IP | 中 | 需注意归属 |
| 黑名单数据中心 IP | 低 | 已被封 |

**建议**：解锁流媒体优先选原生 / 住宅 IP 节点，并在购买前用解锁测试站验证。

## 晚高峰实测方法论

- **采样窗口**：连续 7 天晚 20:00-22:00 记录延迟/丢包。
- **对比基线**：同一节点凌晨值与晚高值相减，差 >80ms 视为超载。
- **多人交叉**：社群多人同节点数据取中位数，排除个例。
- **结论有效性**：单次测试不具备代表性，至少 3 天样本。

## 常见问题 FAQ

**Q：节点越多越好吗？**
A：不是。核心区域专线质量远比数量重要。

**Q：为什么晚高峰变慢？**
A：节点满载。选有动态扩容、控制单节点人数的机场。

**Q：如何判断节点是否真落地宣称地区？**
A：tracert 看路由最后一跳 IP 归属地，或用 ipinfo 查出口 IP。

**Q：url-test 和 fallback 怎么选？**
A：日常用 url-test 自动选优；稳定性优先用 fallback。

**Q：游戏该选哪个区域？**
A：HK/TW 延迟最低，JP 次之，按游戏服务器位置定。
